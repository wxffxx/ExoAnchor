## 1. Summary

| Item | Result |
| --- | --- |
| Full network OTA (upload, SHA-256 check, slot switch, reboot, read-back) | All four upgrades (A, B, C, final) read back the new version and `valid` |
| Resume after a network break | TCP dropped after the device had written 8192 bytes; resuming from the queried offset succeeded; a stale offset and an early finish were rejected |
| Hard reset mid-upload | Reset after 4096 bytes written; the old version booted normally and the unfinished session was cleared |
| Rollback after a first-boot failure | The fault image restarted before startup confirmation and the bootloader rolled back to the previous version automatically; the whole sequence is visible in the serial log |
| Bad-package rejection | Anonymous upload, malformed JSON, oversized image, wrong SHA-256 and truncated image were all rejected, boot partition unchanged |
| Defect: truncated package borrows the old image tail | B accepted a 4096-byte truncated package and switched the boot partition; C rejects it after the fix |
| Defect: abandoned session not cleaned up on its own | A was still busy after 310 s; C had cleaned up by itself after 310.2 s, with no reboot in between |
| Defect: default-credential 403 branch returns success | Reproduced and fixed with a host regression; not verified on the board |
| Independent flash verification | Final application, original factory application, original bootloader and partition table match |

All three fixes are in main: the current main `ota_runtime_module.inc` contains the second image
verification bounded by the received bytes (`received_image`, `.size = written`) and
`ota_upload_session_watchdog_task` (task name `ota_expiry`); `web_server.c` calls
`ota_upload_session_watchdog_start()` at startup; and the default-credential branch in
`ota_settings_module.inc` returns `ESP_ERR_INVALID_STATE` once the 403 has been sent. The three
host regressions run in `scripts/check-all.sh`. The fault-injection code was used only for this
experiment and never entered the repository.

## 2. Method

**Path**: a host script logs in over the device's HTTPS API and upgrades through the chunked
upload endpoints (start / chunk / finish / status / abort / reboot) with 64 KiB chunks; on finish
the device returns the SHA-256 of the whole image. Before every upload the script checks that
`/api/capabilities` reports the PrototypeV2.4 board.

**Serial only on the side**: used to read the chip identity, take the pre-test backup, record
boot logs, hard-reset through RTS and run `verify_flash`; no application was written over serial
in place of OTA. Before testing, the full 16 MiB flash was read out as a recovery backup
(SHA-256 `5e60455d…`).

**Images**: five Dev builds, each with its own version string so they can be told apart in the
serial log and the API:

| Image | Version | Size (bytes) | SHA-256 prefix | Purpose |
| --- | --- | ---: | --- | --- |
| A | `0.87.6-otaA-1008` | 3115840 | `863853d8` | First upgrade from factory |
| FAIL | `0.87.6-otaFAIL-1008` | 3114256 | `37735b1f` | Prints an injection marker and calls `esp_restart()` before startup confirmation |
| B | `0.87.6-otaB-1008` | 3112368 | `d18a6383` | Reproduces the defects |
| C | `0.87.6-otaC-1008` | 3112560 | `9bf1adce` | Fixed build |
| Final | `0.87.6-ota-1008` | 3112544 | `1bd2dc3d` | Full upgrade through the fixed service |

**Network break**: the request header declares `Content-Length: 65536`, only 8192 bytes are
sent, then the real TCP connection is closed. The script then queries `upload/status` for the
device-side offset, deliberately resends from offset 0 and calls finish early, confirms both are
rejected, and resumes from the offset the device reported until the end.

**Fault cases**: after each case the script checks that the boot partition is unchanged,
`busy=false`, and no session is active. The truncated image is the first 4096 bytes of a
complete image, sent with the correct SHA-256 of those 4096 bytes.

**Abandoned session**: start a 4096-byte session, send no further upload requests, wait 310 s
(the session limit is 300 s), then read only `/api/ota/status` and `/api/automation/status`,
without touching `upload/status`; compare `boot_id` before and after to rule out a reboot.

**Rollback**: the serial log must show the fault image's version and injection marker first and
then version A, rather than inferring the rollback only from the version shown on the web page.

## 3. Problems and root causes

### 3.1 A truncated package borrows the old image tail in the target slot

Symptom: B runs from ota_1 while the target slot ota_0 still holds A. Uploading the first 4096
bytes of A made finish return 200 with `reboot_required=true`, and the boot partition switched to
ota_0. The same case on A returned 400 `ESP_ERR_OTA_VALIDATE_FAILED`; the defect appears only
when the target slot still holds the same old image.

Root cause: `esp_ota_end` validates the whole partition. OTA erases and writes sequentially, so
only the first 4096 bytes were overwritten and the rest was still the old copy of the same
image; the partition as a whole looked like a complete, valid image.

Fix: `ota_finish_update` takes a new `written` parameter and, after `esp_ota_end`, runs
`esp_image_verify` again over only the bytes actually received in this transaction (including
the image checksum, hash and any required signature); on failure the boot partition is not set.
Chunked upload, whole-image upload and manifest download all share this code.

Verification: the host regression `test_ota_image_extent_runtime.py` fails on the old code. On
the board with C, repeating the case with the first 4096 bytes of B, the chunked endpoint returned
400 `ESP_ERR_IMAGE_INVALID` and the whole-image endpoint returned 500 `ESP_ERR_IMAGE_INVALID`; the
boot partition did not change in either case.

### 3.2 An abandoned upload session waits for the next request to be cleaned up

Symptom: on A, after a session was started and no further requests were sent,
`/api/ota/status` still reported `busy=true` after 310.1 s; the session was cleared only once
`upload/status` was requested.

Root cause: the 300 s no-progress limit was checked only inside upload-related requests. Once
a client gives up there are no more requests, so the session, the maintenance hold ("firmware
upload maintenance", which blocks manual operation) and the video pause stay in place.

Fix: a new standalone task `ota_expiry` (4096-byte stack) tries every 1 s to take the OTA lock
without waiting; when it gets the lock it applies the existing 300 s limit, clears the session,
releases the maintenance hold and lifts the video pause. Holding the lock excludes writes and
finish, so an in-progress request is never interrupted; the flash cleanup is kept off the shared
`esp_timer` task.

Verification: C waited 310.2 s without touching the upload endpoints and reported `busy=false`,
an empty maintenance operation list, the status message "chunked OTA session expired and was
aborted", and the same `boot_id` before and after. The host regression
`test_ota_session_runtime.py` covers skipping while the lock is held and cleaning up only once on
expiry.

### 3.3 The default-credential 403 branch returns success

Root cause: when the user still has the default credentials, `ota_require_auth` sends a 403 but
returns the send function's result directly; a successful send is `ESP_OK`, which the caller
treats as authorized.

Fix: return `ESP_ERR_INVALID_STATE` when the 403 was sent successfully, and the send error when
it was not.

Verification: the host regression `test_ota_auth_runtime.py` failed before the fix and passes
after it. Verifying this branch on the board would require resetting the board's account to the
default credentials, which this round did not do; on the board only the 401 for anonymous upload
was tested.

## 4. Final measurements

**Upgrade chain** (in time order):

| Step | Action | Result |
| --- | --- | --- |
| 1 | factory `0.87.6-dev` → A (ota_0), with a network break | Resume completed, SHA-256 matched, A / ota_0 / `valid` after reboot |
| 2 | Fault cases and abandoned session on A | All bad packages rejected; the abandoned session was still busy after 310.1 s (reproduces 3.2) |
| 3 | RTS hard reset after uploading 4096 bytes to A | A booted normally, `busy=false`, no active session |
| 4 | A → FAIL (ota_1) | The fault image restarted about 4.6 s into boot, before confirmation; the bootloader rolled back to A / ota_0 / `valid` |
| 5 | A → B (ota_1), with a network break | B / ota_1 / `valid`; 3.1 then reproduced during the fault cases |
| 6 | B → C (ota_0) | C / ota_0 / `valid`; the fixes for 3.1 and 3.2 passed retest |
| 7 | C → final (ota_1), with a network break | Final / ota_1 / `valid`, no active upload |

**Fault cases**:

| Case | A | B | C |
| --- | --- | --- | --- |
| Anonymous upload | 401 | 401 | 401 |
| Malformed JSON | 400 | 400 | 400 |
| Oversized image (0x400001 bytes) | 400 `ESP_ERR_INVALID_SIZE` | 400 `ESP_ERR_INVALID_SIZE` | 400 `ESP_ERR_INVALID_SIZE` |
| Wrong SHA-256 | 400 `ESP_ERR_INVALID_CRC` | 400 `ESP_ERR_INVALID_CRC` | 400 `ESP_ERR_INVALID_CRC` |

**Final state**: `0.87.6-ota-1008`, running = boot = ota_1, `valid`, no active upload. The final
image is 3112544 bytes, SHA-256 `1bd2dc3d…`.

**Settings preserved**: account credentials (login with the same credentials), device label,
hostname, IPv4, OTA settings, and the Dev / embedded Agent / external MCP build switches were
unchanged after the whole chain. This is a semantic check of selected settings, not a claim
that the NVS bytes are identical.

**Software verification**: Dev and Stable (V2.4) builds pass; Stable was only build-tested and
the board ran Dev. The full `check-all` passes under Python 3.11, including 130 MCP tests, 126
Toolkit tests and the 3 new OTA runtime tests (the actual firmware functions extracted,
compiled with stubs, and run).

## 5. Open issues

- Only hard resets and startup failures were tested; real power loss, brownout, flash
  corruption and repeated endurance cycles were not.
- Resume works only for a session within the same boot; after a hard reset the upload starts
  over, and resuming across reboots is not supported.
- Remote HTTPS manifest download was not tested end to end; the whole-image endpoint was only
  tested for truncation rejection, and full upgrades mainly used the chunked endpoints.
- The test client used self-signed TLS without certificate verification against this
  identity-checked board; the certificate-trust deployment flow is not proven.
- Firmware signing, board binding inside the image, and an overall request deadline are not
  yet handled. This round is validation on one development board and does not mean OTA meets
  the requirements for a formal release.
- The default-credential 403 branch has only a host regression, no on-board verification.
- The baseline firmware already had degraded Agent Task Service log-directory and SD access; this
  round only kept the feature switches and did not accept the full Agent runtime.
- Under the default uv Python 3.12.13, 3 Toolkit deep-JSON tests fail; the related code was not
  changed in this round and these failures are not counted as OTA results. Commit `7acdf06f` on
  2026-10-16 switched the Toolkit's GUI transport and release metadata parsing to a JSON nesting
  depth limit that does not depend on the Python version; this document has not re-run them under
  Python 3.12 to confirm.

# 0.88 AzureDanube 视频流实验记录

- 时间：2026-10-24 — 2026-10-27
- 固件：0.87.6-dev 之后的视频流改动，统一随 `0.88.0-dev AzureDanube` 发布
- 硬件：ExoAnchor PrototypeV2.4（ESP32-P4 rev3.2，32 MB PSRAM @ 250 MHz），MS2109 USB 采集，
  HDMI 源为 Mac mini
- 逐项改动清单见[固件版本历史](../../device/ESP32P4/firmware/docs/FIRMWARE_VERSION_HISTORY_zh.md)；
  本文记录实验方法、数据、根因和走过的弯路

## 1. 结论

| 指标 | 实验开始时 | 0.88.0 |
| --- | --- | --- |
| H.264 720p30 端到端（采集卡交付 → 浏览器上屏） | 约 350 ms（设备 51 + 浏览器 300） | 约 32 ms |
| 关键帧（IDR）处停画 | 每个 IDR 约 280 ms | 无 |
| P 帧色度漂移（发紫） | 每个 GOP 内逐帧累积 | 无 |
| 720p30 / 1080p25 帧率（HTTPS） | 不稳定，常见首帧超时 | 30.0 / 24.6 fps |
| 体感延迟（与 VNC 客户端并排对比，720p30） | — | 约 120 ms |

最大的一段延迟不在固件里，而在浏览器：页面把 Annex B 码流直接交给 WebCodecs，解码器按
H.264 level 的上限压住 9 帧才输出。这一点在给页面加上逐帧“到达 → 上屏”计时之前一直看不到。

## 2. 测试方法

**链路**：MS2109 输出 MJPEG → P4 硬件 JPEG 解码为 YUV420 → P4 硬件 H.264 编码 → WebSocket
（HTTPS 下经 TLS）→ 浏览器 WebCodecs 解码 → canvas。

**三处计时**：

1. 设备侧：固件在 UVC 帧回调记下采集时间戳，H.264 发送完成时累计
   `latency_avg_us/latency_max_us`，并分别记录解码、编码、发送耗时（`/api/video/status` 的
   `h264_runtime.chain_metrics`）。
2. 线上：独立的 WebSocket 客户端直接拉 H.264 码流，统计每个访问单元（AU）的到达间隔、IDR
   前后的间隔和大于 1.5 / 2 / 3 倍帧周期的间隔次数，同时读取设备侧分段计时。
3. 浏览器：KVM 页记录每帧 WebSocket 到达到上屏的时间，显示在状态栏。

**独立基准**：另做了一个只含 UVC + JPEG 解码 + H.264 编码的最小固件（不含 HTTPS、Agent、
以太网等服务），用于测硬件上限，并对照判断问题出在编解码链路还是产品固件环境。

**注意事项**：

- KVM 视频租约约 10 s 不续即过期；测量工具必须在一条长连接上续租。每新建一条 HTTPS 连接，
  ECDHE 握手都会让视频管线停顿约 200 ms，频繁新建连接的外部工具会自己制造周期性卡顿。
- 切换分辨率要在持有租约时进行，否则模式只保存、不生效，测到的是旧模式。
- 静态桌面和播放视频的码率相差数倍，不同轮次只比较同类内容。

## 3. 硬件上限

独立基准（原厂 esp_h264 1.3.7，PSRAM 250 MHz，每项 120 帧均值）：

| 分辨率 | 内容 | JPEG 大小 | 硬件 JPEG 解码 | 硬件 H.264 编码 | 串行 fps | 流水线 fps |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 1280×720 | 桌面纹理 | 154 KB | 8.2 ms | 14.7 ms | 43.7 | 61.2 |
| 1280×720 | 全帧噪声 | 736 KB | 11.8 ms | 14.5 ms | 38.0 | 61.0 |
| 1920×1080 | 桌面纹理 | 347 KB | 18.4 ms | 33.2 ms | 19.4 | 27.2 |
| 1920×1080 | 全帧噪声 | 1.66 MB | 26.5 ms | 32.7 ms | 16.9 | 27.0 |

- H.264 编码耗时只与像素数成正比（约 62 Mpixel/s），与内容无关；1080p 一帧约 33 ms，与解码
  并发后 36–38 ms，所以 1080p 的上限是 25–28 fps，1080p30 不可达。固件因此把 1080p 的 H.264
  封顶在 25 fps。
- MS2109 的 4:2:2 JPEG 解码开销按像素数而非字节数计，1080p 约 24–26 ms。
- PSRAM 200 → 250 MHz 不改变单独编码时间，但把并发编码从 40.5 ms 降到 35.8 ms，1080p 流水线
  从 25 提到 28 fps；H.264 构建因此固定使用 250 MHz。

## 4. 问题与根因

按发现顺序排列。

### 4.1 H.264 出口绕过了 TLS

现象：H.264 连接建立后立即断开，页面提示“H.264 连接断开，正在自动重连”。

根因：发送函数在握手后被替换成直接 `send(fd)`，视频服务迁到 444 端口 TLS 后，WebSocket 帧
以明文写进 TLS 套接字，客户端收到非法记录后断开。另一处：页面在 HTTPS 下连的是 443 同源端口，
而 H.264 路由只注册在 444。

修复：自行组 WebSocket 帧，经会话传输函数（TLS 写）循环 send-all；页面从构建配置读取视频端口。
修复后 1080p25 经 TLS 实测 23.5 fps。

### 4.2 P 帧逐渐发紫：去块缓冲落进了 DMA 无法访问的内存

现象：每个 GOP 的 IDR 正确，之后的 P 帧色度均值逐帧累积偏高，宏块行末尾出现条纹，下一个 IDR
复位。静态桌面下 P 帧仍有 40–280 KB，说明编码器的参考帧与解码端重建不一致。

排查：独立基准始终干净，产品固件始终漂移。逐项排除了固件对编码器的补丁、解码与编码并发、
PSRAM 时钟、网络出口、帧率、ISR 优先级和所在核、DMA 仲裁等因素。关掉 HID 和目标机 UART 后
1080p 变干净，但用同样大小的内部 RAM 占位代替这两个外设后又漂移，说明外设只是改变了内部堆的
布局。最后记录所有内部缓冲地址和 DMA AXI 错误计数，找到差别：

| 版本 | 去块临时缓冲 `db_tmp` 地址 | DMA AXI 写响应错误 |
| --- | --- | --- |
| 漂移 | 0x5010xxxx（LP/RTC SRAM） | 非零 |
| 干净 | 0x4ffbxxxx（L2MEM） | 0 |

根因：esp_h264 1.3.7 用 `MALLOC_CAP_INTERNAL` 申请 `db_tmp`（1080p 约 15.4 KB）和 DMA 描述符；
ESP32-P4 的 LP(RTC) SRAM 和 SPM 也带 INTERNAL 能力，但 H.264 DMA 访问不到。产品固件在会话开始时
内部堆已碎片化，`db_tmp` 便落到 RTC RAM，去块滤波往返失败，参考帧带着陈旧数据逐帧累积。独立
基准的堆几乎是空的，所以从未复现。

修复：构建期补丁让 esp_h264 的内部分配一律附加 `MALLOC_CAP_DMA` 并按缓存行对齐；开机早期与
138 KB 参考行窗一起预留 `db_tmp`，每个编码器句柄复用。修复后 720p30 和 1080p20/25 全程色度
稳定、零解码错误。该修复已提交上游（espressif/esp-h264-component PR #23），上游已在内部合入，
尚未发版；在包含它的版本发布之前，固件保留自己的开机预留。

### 4.3 会话时的内部 RAM 门槛把 H.264 卡死

现象：“首帧超时，自动重连仍未恢复”，`resource_error=ESP_ERR_INVALID_STATE`，会话从未启动。

根因：会话准入门槛（空闲 ≥ 24 KB、最大块 ≥ 18 KB）是在 `db_tmp` 开机预留之前定的；预留吃掉了
这部分余量，正常开机后只剩约 28 KB 空闲、最大块 12.8 KB，门槛永远不满足。此时会话真正还需要的
严格内部内存只有 DMA 描述符、SPS/PPS 小缓冲和一个 4 KB 的解码任务栈。

修复：门槛改为 12 KB / 6 KB。教训：任何“预留更多内部 RAM”的改动，都要同时复核后面以绝对值写死
的内存门槛，并在完整开机后检查 `/api/video/status` 的 `resource_error`。

### 4.4 码率突然暴跌，切换模式后恢复

根因：esp_h264 1.3.7 的硬件码率控制把累计比特误差无上限累加，且只要误差超过一帧预算的 20%
就强制 QP +1。一段超预算的画面之后，QP 逐帧爬到上限，码率坍缩到几十 kbps，直到重建编码器才复位。

修复：只把 esp_h264 1.4.1 中 `rc_end()` 的两处改动（累计误差限幅为 1 秒码率预算、强制步进改为
最小步进）以构建期补丁套到 1.3.7 上。没有整体升级码率控制器：同一张静态 720p 图，上游新版本
只有 27–31 dB PSNR，1.3.7 为 72 dB，行为差异需要另行评估。

### 4.5 关键帧处的周期性顿挫

IDR（720p 约 120 KB、1080p 约 240 KB）比 P 帧大一到两个数量级，经软件 TLS 发送要多 20–40 ms。
对策依次为：

- 视频服务任务优先级提高一档，避免与 UI 服务器上的 TLS 握手同级轮转（握手压力下最大停顿从
  220–905 ms 降到 170 ms）；
- H.264 构建使用 16 KiB TLS 记录、32 KiB TCP 发送缓冲，每帧发送 720p30 3.4 → 1.5 ms；
- GOP 25 → 120 → 240（编码器字段为 8 位，240 即上限）。视频走无损 WebSocket，新客户端本就会
  拿到强制 IDR，长 GOP 没有恢复代价。

### 4.6 成对晚到的帧：Nagle

现象：设备侧时间戳均匀，浏览器侧到达间隔却呈“66 ms、1 ms”成对出现（640×480 下 16% 的帧）。

根因：视频 socket 没有设置 `TCP_NODELAY`。480p 的 AU 只有 2–5 KB，末尾不足一段的数据被 Nagle
攒着等对方的延迟 ACK，两帧一起发出。

修复：H.264 WebSocket 和 MJPEG 流都设置 `TCP_NODELAY`。640×480 @30 下大于 66 ms 的到达间隔从
294 次降到 2 次，p95 从 67 ms 降到 36 ms。

### 4.7 每 2 秒一次的卡顿：串口日志阻塞

现象：修掉 Nagle 后仍有每 2.0 s 一帧晚到约 20 ms，与 HTTP 请求、TLS 握手、以太网链路轮询都无关。

排查：在固件里加慢帧分解日志，发现视频发送任务并不忙，而是有 20 ms 没被调度。

根因：推流任务每 2 s 用 `ESP_LOGI` 打一行约 300 字节的链路统计；控制台 UART 是 115200 波特的
阻塞输出（约 20 ms），同核上优先级更低的视频发送任务在这 20 ms 内拿不到 CPU。

修复：统计改为 `ESP_LOGD`（仍可从 `/api/video/status` 读取），诊断日志只写内存日志环、不走 UART。
720p30 下非 IDR 的长间隔从约 35 次/分钟降到 8 次且不再有周期。

### 4.8 流水线重叠等待：低延迟模式

为了让下一帧的解码与当前帧的编码在两个核上并行，固件原先把已解码的帧压到下一帧到达后才编码，
代价接近一个采集周期。现在每 2 s 比较“解码 + 编码”与帧周期：低于周期即进入低延迟模式（解码完
立即编码发送），超过 108% 退回重叠路径保吞吐。

| 档位 | 重叠路径设备侧 | 低延迟模式设备侧 |
| --- | ---: | ---: |
| 720p30 | 50.6 ms | 26.5 ms |
| 1080p15 | 105.8 ms | 59.4 ms |

1080p20/25 的解码 + 编码约 64 ms，超过 50 / 40 ms 的帧周期，只能走重叠路径。

### 4.9 浏览器压住 9 帧：Annex B 与 AVCC

现象：设备侧已降到约 30 ms，但 Chrome 中“到达 → 上屏”中位 301 ms，每个 IDR 处停画 280 ms；
`decodeQueueSize` 为 0，切换软件解码也一样。

分析：码流 SPS 为 Baseline、level 4.1、`max_num_ref_frames=1`，VUI 没有 `bitstream_restriction`，
解码器只能按 level 的 DPB 上限（720p 为 9 帧）延迟输出。在页面里并行跑两个解码器喂同样的数据：

| 输入格式 | 出帧延迟 中位 / p90 / 最大 | 待输出帧 |
| --- | --- | --- |
| Annex B（带内 SPS/PPS，无 description） | 301 / 302 / 318 ms | 9 |
| AVCC（avcC description + 长度前缀，SPS 补 `bitstream_restriction`） | 1 / 2 / 10 ms | 0 |

修复：页面改为 AVCC 输入，并给设备 SPS 补上 `num_reorder_frames=0`、
`max_dec_frame_buffering=max_num_ref_frames`（比特级改写，有单测）。之前的“延迟超限断流”
和“每几秒一顿”都是这同一个 9 帧缓冲。

### 4.10 采集卡整幅偏色：源头问题

现象：偶发整幅偏色（白 → 品红、暗部 → 绿），与 4.2 不同，不随 GOP 变化，在三种状态间瞬间切换。

排查：直接抓 MS2109 输出的原始 MJPEG，源头帧本身就偏色；10 分钟 H.264 码流零解码错误、无编码器
漂移特征。HDMI 插拔、短时电源轨断电、P4 重启都无效，整套设备长时间断电后恢复，且发生频率随时间
上升。判断为 MS2109 过热后把 RGB 输入误判为 YCbCr。

缓解：固件新增“冷启动采集卡”（30–60 s 断电后上电，默认 45 s）；KVM 页每秒采样画面，U、V 同时
偏高连续 3 次即提示并提供一键冷启动。只用 U 做判据会把蓝色画面误判为偏色。诱因尚未确认，固件只能缓解。

## 5. 试过但没有采用

| 方案 | 结果 | 原因 |
| --- | --- | --- |
| 加深 USB 等时 URB 环 | 1080p 帧率无改善 | 驱动回调间隔最大 1.35 ms，环深度不是瓶颈；更深的环还会挤掉参考行窗需要的连续内部 RAM |
| JPEG 解码前先拷贝出 UVC 缓冲 | 独立基准 1080p 17 → 24 fps；产品固件反而慢约 1.8 fps | 产品固件里摄入侧没有丢帧，拷贝的 2–3 ms 直接落在关键路径上；保留为默认关闭的 A/B 开关 |
| 参考行窗与 `db_tmp` 放到 PSRAM | 编码时间固定增加约 63%，720p30 守不住 | 两者是逐宏块的热路径，只能放内部 RAM |
| 硬件 AES-GCM | Dev H.264 镜像开机 3.8 s 循环重启 | AES DMA 描述符分不到内部 DMA 内存，CTR_DRBG 种子失败 |
| 明文 HTTP | 设备侧省约 25 ms，浏览器多约 300 ms | `http://IP` 不是安全上下文，没有 WebCodecs，只能走 MSE；开关保留为台架选项 |
| 整体升级 esp_h264 码率控制器 | 静态画面画质明显下降 | 见 4.4 |
| 断电前先关 UVC 流并释放 USB 设备 | 重新枚举时触发 IDF 断言，整板重启 | 已撤回；采集卡断电后 UVC 重开会有 1–10 s 的 `EP Alloc error`，之后自行恢复 |

## 6. 0.88.0 最终实测

2026-10-27，PrototypeV2.4，HTTPS（台架免登录镜像），H.264 每档 30–40 s：

| 档位 | 实测 fps | 解码 + 编码 + 发送 | 设备侧延迟 | 路径 | 背压丢帧 |
| --- | ---: | --- | ---: | --- | ---: |
| 720p30 | 30.0 | 12.9 + 14.7 + 1.5 ms | 30.9 ms | 低延迟 | 0 |
| 1080p15 | 15.0 | 26.4 + 33.2 + 2.7 ms | 64 ms | 低延迟 | 0 |
| 1080p20 | 20.0 | 26.4 + 37.4 + 1.5 ms | 92 ms | 重叠 | 4（启动时） |
| 1080p25 | 24.6 | 26.4 + 37.9 + 1.7 ms | 107 ms | 重叠 | 4（启动时） |
| 1080p30 | — | — | — | H.264 不提供（上限 25 fps），可用 MJPEG | — |

- 720p30 的 IDR 约 137 KB，IDR 前的到达间隔约 59 ms，其余帧间隔中位 33.3 ms、p95 34.3 ms，
  40 s 内没有超过两倍帧周期的间隔。
- 开机后约 1 分钟内的第一轮测量出现过 18 次晚到一帧（约 67 ms），随后各轮均干净，判断为开机预热。
- MJPEG 720p 正常出流（约 182 KB/帧）。
- 浏览器侧（Chrome，HTTPS，WebCodecs）到达 → 上屏中位 1 ms、p90 2 ms。

## 7. 遗留问题

- HTTPS 下 IDR 的 TLS 加密每 8 s 带来一次 21 ms（720p）/ 38 ms（1080p）的晚到；Dev 配置因内部
  DMA 内存不足无法使用硬件 AES。页面提供可选的“一帧节拍缓冲”，代价是多一个帧周期的延迟。
- 采集卡断电后 UVC 重开会有 1–10 s 的 `EP Alloc error: ESP_ERR_NO_MEM`，疑似 vendored
  usb_host_uvc 的停止 URB 环补丁延迟释放了旧设备的管道，待单独排查。
- 慢帧日志偶见解码完成到编码开始之间 55–62 ms 的空档，与 TLS 无关，原因未明。
- H.264 构建空闲时内部 RAM 约 20 KB、最大块约 14 KB；页面重连带来的 TLS 握手会把它短暂压到
  7 KB 左右。后续任何占用内部 RAM 的改动都要先在 H.264 构建上复核。
- MS2109 可能出现原因不明的热偏色，目前没有发现诱因。

# 固件修改验证规程

本规程覆盖 Dev 源码树的浏览器会话与导航、设置文本、HTTP 响应正文、静态 IPv4 配置、
局域网发现以及视频与 KVM 连接回归。它说明应如何取得证据，不代表某块设备已经通过验证。
Dev 源码目录名为 `v0.86.6-dev`；实际运行版本以该目录的
[`CMakeLists.txt`](../../device/ESP32P4/firmware/v0.86.6-dev/CMakeLists.txt)
及构建产物为准。

## 1. 无硬件的主机测试

首次使用时，在仓库根目录创建虚拟环境并安装主机测试的 Python 依赖：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install \
  -r device/ESP32P4/firmware/v0.86.6-dev/tests/host/requirements.txt
```

然后在仓库根目录运行：

```bash
PYTHON="$PWD/.venv/bin/python" \
  ./device/ESP32P4/firmware/v0.86.6-dev/tests/host/run.sh
```

依赖为支持 C11 的 C 编译器（默认 `cc`，可通过 `CC` 指定）、Python 3.10+
和 Node.js 18+，以及 `tests/host/requirements.txt` 中的 Python 依赖。
入口会在运行测试前检查这些工具和 `requests` 模块；`PYTHON` 可指定已有环境的
解释器，此时无需重复创建虚拟环境。
Dev 测试所需的 cJSON 源码固定在 `tests/host/vendor/cjson/`，与 ESP-IDF 5.5.5
使用的版本一致；安装 Python 依赖后，该入口可离线运行，无需安装 ESP-IDF。
第三方来源和许可证以该目录的说明文件为准。

首次配置本机环境时，应在未激活 ESP-IDF 的新终端中执行完整入口，保存退出码
和全部测试输出。单独运行一个测试通过，不等于完整入口通过。

主机测试使用模拟时钟、网络返回值、浏览器存储或 IDF stub 验证逻辑分支。
重点包括失效认证响应的传播、退出登录后的状态、响应正文超时、设置值的纯文本
呈现，以及网络确认、局域网发现与视频发送的边界条件。它不能证明板级链接、USB/UVC DMA、
真实 TCP 行为或长期运行稳定性。

首次账号创建回归另由整仓入口运行，也可从仓库根目录单独执行：

```bash
node device/ESP32P4/firmware/security-tests/test_browser_setup.mjs
```

整仓安全测试还需要 `pkg-config` 和 OpenSSL 开发头文件及库，详情见
[HTTPS 与首次配置验证说明](SECURITY_TRANSPORT_zh.md#依赖补丁与验证)。
单项浏览器测试通过不能代替这些安全测试。

`v0.86-stable-kvm` 是独立源码树。不要把 Dev 测试通过记录写成 Stable 已通过，
也不要由这次 Dev 主机依赖调整推断 Stable 的依赖要求已经相同。

## 2. 完整固件构建

主机测试之后，使用目标板型对应的 SDK 和独立构建目录编译。以下是现有构建
助手支持的 V2.4 Dev 示例，只执行编译：

```bash
cd device/ESP32P4/firmware/v0.86.6-dev
SI_IDF_EXPORT="$HOME/esp/esp-idf-v5.5.5/export.sh" \
  ./tools/build-firmware.sh \
  --profile dev \
  --board exoanchor-prototype-v2.4 \
  --build-dir build-exoanchor-prototype-v2.4-dev
```

SDK 路径须对应本机实际安装位置。其他板型与 silicon overlay 按
[固件 README](../../device/ESP32P4/firmware/v0.86.6-dev/README.md)
和[配置组合说明](../../device/ESP32P4/firmware/v0.86.6-dev/configs/README.md)
选择；不能把示例中的板型当作已连接设备的身份。普通回归构建保留助手重新生成
`sdkconfig` 的默认行为，不使用 `--reuse-sdkconfig`。

至少保存源码提交及未提交补丁、完整命令、SDK 版本、Board ID、build profile、
生成的 `sdkconfig`、构建退出码和产物校验值。缺少 SDK、依赖下载失败或未完成
编译时，结果记为“未完成完整构建”，不能以主机测试代替。

构建本身不烧录设备。真机验证前须由操作者确认实物身份、匹配镜像及独立恢复
入口；烧录流程按固件 README 执行。本规程不要求控制目标机电源、写 EEPROM
或更新分区布局。

## 3. 浏览器会话与设置文本

在获准使用的测试设备或明确模拟设备响应的测试服务上，记录浏览器版本和
固件标识。使用同一设备 origin 的两个标签页；不同主机名、IP 或端口的浏览器
存储不能混作同一组多标签测试。

| 场景 | 操作与应核对的结果 |
| --- | --- |
| 退出后的首次账号创建 | 在模拟设备中令 `/api/auth/status` 返回 `setup_required`，同时保留该 origin 的旧退出标记；页面仍应能获取首次配置票据并创建账号。票据请求失败时保留退出状态，普通受保护 API 仍须被阻止；只有成功创建并建立会话后才清除退出标记。 |
| 正常登录与刷新 | 登录后刷新 Dashboard、KVM 和 Settings；会话仍有效时页面正常工作，无连续登录重试。 |
| 取消刷新或关闭 | 修改 Settings 中尚未保存的字段，触发离开提示后选择留在此页；输入值与未保存标记应保留，正在进行的请求和轮询继续工作，确认框仍能打开并完成保存。 |
| 取消侧栏导航 | 有未保存修改时点击侧栏其他页面，再选择留在此页；当前页面仍能保存和轮询，链接不应残留忙碌状态。另行检查禁用链接仍不能导航。 |
| 确认离开与缓存恢复 | 确认离开后，实际 `pagehide` 应取消页面请求并清理定时器、连接和租约，重复清理不能重复释放资源。浏览器前进/后退缓存恢复时，按现有策略重新载入页面并初始化资源。 |
| 显式退出 | 在标签页 A 退出，核对退出请求确实到达服务端，且服务端清除会话 Cookie；刷新 A 后仍为未登录。 |
| 多标签退出 | A 退出后检查标签页 B；旧标签页应停止依赖该会话的活动，并进入未登录状态，不能借刷新恢复旧会话。 |
| 延迟的跨标签通知 | 暂停标签页 B，A 退出后重新登录，再恢复 B；旧退出通知不能撤销新会话或重新设置退出标记。 |
| 同页重新登录 | 自动超时退出后，不刷新页面，直接在登录框重新登录；Agent 预览、KVM 租约与需要重新连接的页面资源应能恢复。 |
| Agent 预览租约失败 | 让 `/api/video/lease` 的获取请求超时或返回服务端错误；未成功取得租约前不能启动预览，恢复网络后应能重试。重试等待期间关闭预览、切换面板、退出登录或离开页面，确认不会被旧响应重新开启。 |
| 仅 Cookie 会话 | 在隔离测试浏览器中保留有效 `EA_SESSION` Cookie，清除 JS 存储的认证 token，再刷新；核对状态探测、登录提示和退出操作一致。不要尝试用 JS 读取 HttpOnly Cookie。 |
| 认证失效 | 让已登录会话失效后访问受保护资源；调用方应得到认证失效结果并停止依赖成功响应的后续操作，不能把 HTTP 401 当作成功的空数据。 |
| 响应正文停顿 | 测试服务先返回响应头，再延迟或停住 JSON 正文；请求应在调用方期限内失败并释放活动请求记录，随后正常请求仍可完成。 |
| 设置文本 | 将允许输入的测试说明设为含 `<`、`>`、`&`、引号及类似 HTML 标签的无害字符串；回读摘要应显示字面文本，不能生成新 DOM 元素或改变页面结构。测试结束恢复原值。 |

导航取消回归执行真实客户端脚本，并模拟 Settings 的未保存提示和侧栏点击。
`beforeunload` 或原生链接点击只是可取消的离开意图，不能在此时销毁页面资源；
实际离开由 `pagehide` 负责清理。主机事件模拟不能代替真实浏览器的提示框、
网络发送及前进/后退缓存验证，人工复核时应分别记录这些结果。

不要只检查登录遮罩是否出现。退出后应分别核对服务端认证状态、浏览器 Cookie
和标签页状态。若退出时连接已经中断，应保留失败证据，确认页面没有把无法
确认的服务端撤销报告为成功；恢复连接后重新核对会话。

记录网络日志时遮盖密码、Bearer token 和 Cookie 值。页面截图和 HTTP 状态码
即可证明大多数结果，不需要把完整凭据放入日志或问题单。

KVM HID WebSocket 的主机回归还需注入会话上下文分配失败：失败的握手不能
尝试替换现有键鼠控制权，也不能留下新的会话上下文。内存分配成功、控制权
申请被拒绝时，应释放刚分配的上下文；成功连接断开时，只释放该连接对应的
控制权。较旧连接的断开清理不能撤销后续连接。此项使用故障注入验证，无需
通过耗尽真实设备内存来制造失败。

## 4. 浏览器 HTTP 响应正文超时

使用本地测试服务分别返回正常 JSON、普通文本和错误状态，再在响应头完成后
停住正文。计时范围应包括 `fetch()` 和后续 `response.json()` / `response.text()`，
不能在只收到响应头时就清除超时计时器。

核对超时后 Promise 拒绝、共享 GET 的进行中记录清除，随后对同一路径发出的
请求能够重新完成。另行覆盖正文读取期间的页面导航取消：取消应传递到正文
读取，而不是再重试已经离开的页面请求。

异步登录需覆盖 `202` 作业轮询、较慢的合法成功响应和总期限耗尽，保留同一次
登录请求的身份，并确认总超时生效。测试输出应记录使用的期限值，避免以人工
等待一次成功推断所有超时分支都正确。该项修改属于浏览器接收响应的行为，
不代表设备端上传请求体读取已经增加总期限。

## 5. 网络配置与局域网发现

### 静态 IPv4 的 staged / apply / commit / rollback

这一组会改变测试设备的网络配置，须使用隔离测试网、已记录的原配置和可用的
设备 UART0 恢复入口。目标地址由测试网管理员分配。地址冲突测试只在隔离网
中安排，不以生产网络中的其他主机作冲突对象。

现有 UART0 诊断命令 `network show` 可以只读查看 runtime、active 和 staged
配置。设置页面中的网络摘要是只读入口；不要假定页面包含静态地址编辑功能。
命令格式以设备 `help` 和
[`diag_cli.c`](../../device/ESP32P4/firmware/v0.86.6-dev/main/services/diag_cli.c)
为准；HTTP 配置入口是 `/api/v1/network/config`。

静态配置的网关必须是同子网内的有效主机地址；子网网络地址和广播地址应在
暂存前被拒绝。主机测试覆盖 `/24`、`/25` 和 `/23` 的边界，同时确认空网关
仍被允许，不能仅根据末字节为 `0` 或 `255` 拒绝地址：例如 `/23` 中的
`192.0.2.255` 和 `192.0.3.0` 可以是有效主机地址。本次校验不扩展现有
静态地址对 `/31` 或 `/32` 的支持。

主机持久化回归还应确认非法网关暂存失败时，不改写 NVS、活动配置或已有的
候选配置。加载旧版已保存配置时，同一校验也会生效：非法候选配置会被忽略；
非法活动配置会触发现有恢复逻辑，将网络配置命名空间恢复为默认配置
（DHCP、AutoIP 和默认 hostname）。这类旧配置升级后可能需要重新设置静态地址，
应保留 UART0 恢复入口，并按 DHCP / AutoIP 的实际结果重新确认设备地址，
不能假定旧静态地址仍有效。

1. 记录原始 runtime、active、staged 和 generation。暂存测试配置后，确认仅
   staged 改变，运行中的地址没有提前变化。
2. 应用静态候选，在地址检测尚未处理完成时尝试确认；确认必须被拒绝，不能
   把候选直接写成 last-good。检测成功并且候选实际应用后，才允许确认。
3. 在主机测试中精确安排“ACD 回调已经返回、manager 尚未处理”的时序，分别
   注入成功、冲突和超时；三者都不能在尚未完成应用时提前持久化。真实网络
   中很难稳定命中这个窗口，因此人工点按不能替代该确定性回归。
4. 对成功路径确认后，核对 runtime 与 active 对应同一候选，pending 已清除。
   对冲突或失败路径，核对 active 保持原 last-good，候选不会在下次启动生效。
5. 覆盖 pending 期间再次暂存或重复 apply 的请求；应按明确的事务规则拒绝或
   处理，不得把旧检测结果用于另一份候选配置。
6. 应用一个有效候选后不确认，等待既定的 120 秒确认期限，核对自动回滚。
   另行覆盖显式 `network rollback`，最后确认恢复原配置。

若需要通过重启验证持久化，只在操作者确认本次设备重启不会影响其他验证后
进行；重启不能代替检查 runtime、active 和 pending 的即时一致性。

### 局域网发现的 socket 故障恢复

主机测试注入接收超时设置失败，确认关闭新建的 socket，并经既有退避路径
重新尝试，不能进入没有接收期限的阻塞调用。另行注入不可恢复的 `recvfrom()`
错误，确认关闭失效 socket、等待 1 秒再重建，避免对同一失效描述符持续空转。
正常接收超时（`EAGAIN` / `EWOULDBLOCK`）、被中断的接收（`EINTR`）及空
UDP 数据报应保留当前 socket，不应触发重建。覆盖关闭发现功能时关闭 socket、
撤下 mDNS 服务的行为。

这些故障使用主机边界注入，不要求在实物设备上耗尽资源或人为破坏描述符。
真机上另行核对发现服务关闭、重新开启和网络恢复后的实际响应；主机测试
不能证明所有 lwIP 或网络设备故障均能恢复。

## 6. 慢视频接收端与恢复

Rev3 Dev 默认具备 H.264 构建能力；实际测试仍须记录所选输出模式。普通 Stable
组合保持 MJPEG，不能把 H.264 测试结果推定到未启用该功能的镜像。

主机侧应分别模拟 `send()` 的部分成功、`EAGAIN`、`EINTR`、断连和超时。核心
断言是每次 HTTPD 发送回调受 1,000 ms 绝对期限限制：即使每次调用都发送了一点
数据，也不能无限延长该回调。HTTPD 分别发送 WebSocket 头与 payload，因此
不能把每回调期限误写为每帧总期限；退出等待上限为两次回调预算加 500 ms
调度余量，即 2,500 ms。失败后还应归还帧槽，并检查后续连接是否可以开始。

真机验证使用获准的测试客户端或限速代理，先确认正常视频，再逐步限制接收
速度，并覆盖持续少量读取与停止读取。浏览器限速工具未必限制 WebSocket，
应核对实际流量。记录以下结果：

- 慢连接被结束的耗时、发送错误和帧丢弃统计；
- 视频重新连接或切换输出模式后的恢复情况；
- 同时进行只读状态查询时，控制页面是否仍能响应；
- 重复断开与重连后，可用内存是否恢复，是否遗留 teardown 错误。

端口 81 的兼容 `/api/stream` 与 H.264 WebSocket 共用视频监听服务。若使用该
兼容入口，应另外检查长连接是否阻塞第二个视频请求，并把结果单独记录。
主机发送测试不能证明整条 UVC→JPEG→H.264→浏览器链路的帧率或延迟。

## 7. 记录结论与后续优化

验证记录分别列出“主机测试”“完整板型构建”“浏览器集成”“真机网络/视频”
及“长期运行”，每项填写通过、失败或未执行，并附命令、环境和证据。只有实际
运行的项目才填写通过；板型、SDK 或补丁变化后，注明哪些证据仍适用。

构建期压缩嵌入式网页资源是后续候选优化，当前未改变固件的资源构建或 HTTP
编码方式。对基线 `63b5ce9` 的 14 个 HTML/JS/CSS/SVG 文件，用无文件名、
`mtime=0` 的 gzip level 9 测得总量从 1,107,545 字节降到 282,876 字节，约减少
74.5%。这是资源体积测量，不是固件镜像体积或加载速度实测。落地前需确定
`Accept-Encoding` 不支持 gzip 时的兼容行为，验证构建 profile 注入、二进制
长度、ETag/缓存失效和完整板型构建，再决定是否只嵌入压缩副本。
